# melt-binaries

`melt` (MLT Framework command-line renderer), extracted from the official [Shotcut](https://www.shotcut.org/download/) releases, per OS — so a microservice can fetch a working `melt` without depending on a Docker image/system package that installs MLT/Shotcut and its full desktop-GUI dependency chain.

Source packages (v26.8.1), all from https://www.shotcut.org/download/ (SourceForge):
- Windows: `shotcut-win64-26.8.1.zip`
- Linux: `shotcut-linux-x86_64-26.8.1.txz`
- macOS: `shotcut-macos-26.8.1.dmg`

## Branches

- **`main`** (this branch) — the complete decompressed package for all three OSes together (`windows/`, `linux/`, `macos/` at root), kept as a reference. Not meant to be cloned for deployment — use one of the branches below instead, scoped to exactly the OS you need.
- **`win-full`** / **`win-min`** — Windows, complete vs. trimmed.
- **`lnx-full`** / **`lnx-min`** — Linux, complete vs. trimmed.
- **`mac-full`** / **`mac-min`** — macOS, complete vs. trimmed.

Each `*-min` branch is what you actually want for deployment — same `melt`, ~2.5-4x smaller than `*-full`, content flat at the branch root (no OS-name subfolder):

```bash
git clone --branch win-min --single-branch --depth 1 https://github.com/joseluisbz/melt-binaries.git
```

`*-full` exists only if `*-min` is missing something you need — see "How `*-min` was determined" below for exactly what it excludes (GUI, preview/playback via SDL2, capture card, OpenCV, Whisper transcription, and unused MLT modules).

## How `*-min` was determined

Not guessed — traced from the real binaries and a real `.mlt` project file generated by this pipeline:

1. Extracted each OS's official Shotcut package.
2. Found the `mlt_service` values actually used in a real `.mlt` file: `color`, `qimage`, `affine`, `crop`, `mix`, `qtblend`, `volume`, `avformat-novalidate`.
3. Mapped each service to its owning MLT module (`core`, `xml`, `avformat`, `qt6`, `plus`, `normalize`) via MLT's own `share/mlt*/**.yml` metadata.
4. Resolved the full transitive dependency closure of `melt` + those 6 modules:
   - Linux: `ldd` (via WSL)
   - Windows: `pefile` (Python) — no `dumpbin`/Dependency Walker needed
   - macOS: `lief` (Python) — no macOS machine needed, works from a Windows dev box
5. Anything the OS itself always provides (`kernel32.dll`, `libc.so.6`, `AppKit`, etc.) is excluded — those are guaranteed present on any real install of that OS.
6. All MLT plugin modules are kept in full regardless (not just the 6 traced above) as a cheap safety margin — a few MB each, no meaningful size cost, in case another `.mlt` file uses a service outside this set.

| OS | `*-min` | `*-full` | Reduction |
|---|---|---|---|
| Linux | 189 MB | ~1010 MB | 5.3x |
| Windows | 187.5 MB | ~562 MB | 3.0x |
| macOS | 232.8 MB | ~551 MB | 2.4x |

## Requirements

- **Linux**: needs **glibc >= 2.35** (Ubuntu 22.04+, Debian 12+, Oracle/RHEL/Rocky/Alma **10**+ — NOT 9.x, which ships glibc 2.34 and stays there for its whole lifecycle).
- All platforms: paths are relative to the original package layout (e.g. Linux's `melt-7` expects `../lib` and `../lib/mlt-7` next to it) — keep the folder structure intact, don't flatten it.
